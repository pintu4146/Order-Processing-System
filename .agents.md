# Agent Instructions for Order Processing System

## Shell / Command Rules
- **Always** use `cmd /c "<command>"` when running shell commands on this Windows system.
- Never use bare `powershell` or `bash` commands without the `cmd /c` prefix.
- When chaining commands, use `&` inside quotes: `cmd /c "git add . & git status"`
- Example: `cmd /c "mvn clean compile"` instead of `mvn clean compile`

## Git Branching Strategy (MANDATORY)

### Branch Hierarchy
```
main        ← production (protected, merge from stage only)
stage       ← staging/QA (merge from develop only)
develop     ← integration branch (merge from feature/* only)
feature/*   ← feature branches (cut from develop)
```

### Rules — Follow Every Time
1. **Never commit directly to `main`, `stage`, or `develop`**.
2. **Always work on a `feature/*` branch** cut from `develop`.
3. **Branch naming**: `feature/phase-N-description` (e.g., `feature/phase-2-dtos-validation`).
4. **Merge flow**: `feature/*` → `develop` → `stage` → `main`.
5. **After each phase completion**:
   - Commit all changes to the feature branch
   - Merge feature branch into `develop`
   - User will test on `develop`
   - User will promote `develop` → `stage` → `main` when ready
6. **Delete feature branches** after merge to `develop`.
7. **Commit messages**: Use conventional format: `feat:`, `fix:`, `docs:`, `test:`, `chore:`.

### Phase Branch Naming Convention
| Phase | Branch Name |
|---|---|
| Phase 1 | `feature/phase-1-scaffolding` |
| Phase 2 | `feature/phase-2-dtos-validation` |
| Phase 3 | `feature/phase-3-service-layer` |
| Phase 4 | `feature/phase-4-rest-api` |
| Phase 5 | `feature/phase-5-scheduler` |
| Phase 6 | `feature/phase-6-testing` |
| Phase 7 | `feature/phase-7-documentation` |
| Phase 8 | `feature/phase-8-docker` |

### Git Workflow Per Phase
```bash
# 1. Start phase — create feature branch from develop
cmd /c "git checkout develop"
cmd /c "git pull origin develop"
cmd /c "git checkout -b feature/phase-N-description"

# 2. Work on phase — commit frequently
cmd /c "git add ."
cmd /c "git commit -m \"feat: description of change\""

# 3. Complete phase — merge to develop
cmd /c "git checkout develop"
cmd /c "git merge --no-ff feature/phase-N-description -m \"Merge feature/phase-N into develop\""
cmd /c "git branch -d feature/phase-N-description"

# 4. User promotes when ready
# develop → stage → main (user-controlled)
```

## Database Migration (Flyway)

### Rules
- **Schema is managed by Flyway**, NOT by JPA `ddl-auto`.
- JPA `ddl-auto` is set to `validate` in all profiles — it only checks, never creates/modifies tables.
- **All schema changes** must go through a versioned Flyway migration script.
- Migration scripts live in: `src/main/resources/db/migration/`
- Naming convention: `V{N}__{description}.sql` (double underscore, e.g., `V1__init_schema.sql`)

### Adding a New Migration
1. Create a new file: `V{next_version}__{description}.sql`
2. Write the DDL/DML SQL
3. The migration runs automatically on app startup
4. **Never edit an existing migration** — create a new one instead

### Per-Environment Behavior
| Profile | Flyway Clean | Logging |
|---|---|---|
| `dev` | Allowed | DEBUG |
| `stage` | **Disabled** | INFO |
| `prod` | **Disabled** | WARN |

## Project Context
- **Language**: Java 17
- **Framework**: Spring Boot 3.2.x
- **Build Tool**: Maven
- **Database**: H2 in-memory (all profiles for this assignment)
- **Migrations**: Flyway
- **Containerization**: Docker
- **Config Strategy**: Profile-based YAML configs (`application-dev.yml`, `application-stage.yml`, `application-prod.yml`)

## Architecture Rules
- Modular monolith with layered architecture
- Entities must NEVER be returned from API endpoints — always use DTOs
- All business logic lives in the service layer
- Controllers are thin — validate + delegate
- State transitions are explicit and enforced in the service layer
- Scheduler is thin — calls service methods only

## Code Style
- Follow SOLID, DRY, KISS principles
- Meaningful variable/method names
- Small methods (< 20 lines ideally)
- No deeply nested logic
- Comments only where they add clarity
- Use `BigDecimal` for monetary values
- Use enums for status values

## Testing
- JUnit 5 + Mockito for unit tests
- MockMvc for controller/integration tests
- Test both positive and negative scenarios
- Test edge cases: empty items, invalid status transitions, missing IDs

## File Naming
- Entity classes: singular (`Order.java`, `OrderItem.java`)
- DTOs: descriptive (`CreateOrderRequest.java`, `OrderResponse.java`)
- Tests: `*Test.java` suffix
- Migrations: `V{N}__{description}.sql`

## Documentation
- All docs in `/docs` directory
- README.md at project root
- Keep docs concise but complete
